# 一次真实的 Pages 发布报错

这份记录来自 AI 生活课堂的实际发布过程，整理于 2026 年 10 月 1 日。它示范的是怎样从日志找原因、修改设置，再用实际结果确认。

## 发生了什么

首次提交 `5b4e285` 已成功推送，但 [第一次发布](https://github.com/StupidYang/ai-life-classroom/actions/runs/36865561923) 在 `actions/configure-pages@v5` 失败：

```text
Get Pages site failed … Error: Not Found
```

当时网站地址也返回 HTTP 404。错误发生在 **Configure Pages**，还未执行网站文件上传。

## 怎样确认原因

根据 [GitHub 官方工作流说明](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)，仓库需先启用 Pages，并使用 GitHub Actions 发布。

这次使用已有 GitHub 登录查询了实际仓库：仓库可正常访问，当前账号具有管理权限，但 Pages 配置接口返回 **404**。因此能把问题定位到尚未创建 Pages 站点，而不是直接怀疑网页代码。

其他仓库的 404 也可能涉及权限或地址错误，不能只凭一行报错照搬结论。

## 改了什么

1. 在作者授权下，启用该仓库的 GitHub Pages，发布方式设为 `workflow`。
2. 创建接口返回 **201**；重新读取配置返回 **200**，确认 `build_type` 为 `workflow`。
3. 工作流发布目录继续使用 `dist`，不把文件移到仓库根目录。
4. 增加基础文件检查：`node scripts/check-site.mjs`。这是发布前的额外检查，不是本次 404 的修复原因。

登录凭证只用于授权请求，没有写入网站、工作流或仓库文件。

## 这次可以学到什么

- **推送成功和网站发布成功，是两件事。** 先看失败在哪个步骤。
- **修改前先核对实际配置。** 本次不需要重写 HTML 或调整网页样式。
- **设置保存成功，还要继续检查。** 工作流要成功，网址要能打开，资源也要正确加载。
- **留下可回查的证据。** 提交、运行链接、状态码和实际操作，比“AI 说已修好”更有用。
